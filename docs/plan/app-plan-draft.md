## 2. 전제 (확정)

`CLAUDE.md` "역할" 절에서 옮긴다. 이 절의 내용은 이 문서에서 바꾸지 않는다.

1. 모바일은 데스크톱 Tasty와 다른 형태로 만든다. 데스크톱의 제품 원칙을 그대로 적용하지 않으며, 원칙은 따로 정한다.
2. 플러그인 시스템을 지원하지 않는다. 공식 플러그인 기능은 앱에 내장한다. 데모용 플러그인은 제외한다.
3. 본체 기능인 Explorer도 내장한다.
4. 원격 파일은 SSH 연결로 가져온다. 파일은 SFTP로 읽고, Git 정보는 원격에서 `git` 명령을 실행해 읽는다. 이를 위해 본체에 전용 채널을 추가하지 않는다.
5. 원격 환경이나 원격 Tasty에 필요한 플러그인·기능이 없으면 시각적 피드백만 보여 준다.
6. Kotlin + Jetpack Compose로 만들고, 본체와 맞아야 하는 로직은 Rust 크레이트를 UniFFI로 공유한다.

지침은 "그 밖의 구체적인 범위는 아직 정하지 않았다"고 적는다. 그 범위는 4절에 선택지로 적는다.

## 3. 기능 후보

### 3.1 Explorer (전제 3, 4)

- 내용: SSH로 접속한 원격 호스트의 파일과 폴더를 SFTP로 탐색하고 연다.
- 전제로 정해진 것: 내장한다. 파일은 SFTP로 읽는다.
- 정하지 않은 것: 편집 여부(4.4), 열 수 있는 파일 종류와 뷰어 연결(3.3, 5절 `tasty-file-format`), 캐시(4.8).

### 3.2 Git 정보 (전제 4)

- 내용: 원격 저장소의 상태, 기록, 차이 등을 원격에서 `git` 명령을 실행해 읽고 보여 준다.
- 전제로 정해진 것: 원격 `git` 명령으로 읽는다. 본체에 전용 채널을 만들지 않는다.
- 정하지 않은 것: 보여 줄 범위(상태만 / 기록·차이까지 / worktree까지), 쓰기 동작(커밋 등)을 넣을지.

### 3.3 내장할 공식 플러그인 기능 후보 (전제 2)

본체 `89efb5602`의 `crates/tasty-plugin-*` 중 실제 플러그인(`tasty-plugin.toml`이 있는 크레이트)이다. 각 항목을 모바일에 넣을지는 정하지 않았다.

| 본체 플러그인 | 본체에서 하는 일 | 모바일에 넣을 때의 선택지 | 고려할 점 |
|---|---|---|---|
| `tasty-plugin-markdown` (Markdown Viewer) | Markdown 파일을 webview로 보여 준다 | 넣는다 / 넣지 않는다 | Explorer에서 연 원격 `.md` 파일을 보는 장면과 맞는다. Android WebView 또는 Compose 렌더러 중 고른다 |
| `tasty-plugin-git-viewer` (Git Viewer) | 읽기 전용 git status/log/diff 팝업 | 넣는다(3.2와 합친다) / 넣지 않는다 | 본체는 로컬 저장소를 git2로 읽는다. 모바일은 원격 `git` 명령으로 읽는다는 전제가 있다 |
| `tasty-plugin-image` (Image) | 이미지 보기와 그림판 캔버스 | 보기만 / 보기+그리기 / 넣지 않는다 | 그림판은 터치 입력과 맞지만 범위가 커진다 |
| `tasty-plugin-html` (HTML Viewer) | HTML을 webview overlay로 보여 준다 | 넣는다 / 넣지 않는다 | 원격 HTML의 상대 경로 자원(이미지·CSS)을 SFTP로 어떻게 가져올지가 걸린다 |
| `tasty-plugin-clipboard-viewer` (Clipboard Viewer) | 현재 시스템 클립보드를 읽기 전용으로 본다 | 넣는다 / 넣지 않는다 | Android는 백그라운드 클립보드 읽기를 제한한다. 모바일에서 쓸모가 작을 수 있다 |
| `tasty-plugin-claude` (Claude Code) | Claude Code CLI 연동(자식 관리, 상태 알림) | 상태 보기만 / 조작까지 / 넣지 않는다 | 본체의 터미널·서피스에 기대는 기능이다. 원격 Tasty와의 관계(4.3)와 터미널 여부(4.2)에 따라 달라진다 |
| `tasty-plugin-codex` (Codex) | Codex CLI 연동 | 위와 같다 | 위와 같다 |
| `tasty-plugin-agent-stream` (Agent Stream) | AI 에이전트 세션 기록을 따라 읽고 이벤트로 정리한다 | 넣는다 / 넣지 않는다 | 원격 파일을 SFTP로 따라 읽을 수 있는지, 원격 Tasty가 필요한지 확인해야 한다 |

목록에서 뺀 것:

- `tasty-plugin-mesh-demo`: 데모용(egui-mesh 채널 PoC)이라 전제 2에 따라 제외한다.
- `tasty-plugin-agent-common`, `tasty-plugin-manifest`, `tasty-plugin-protocol`, `tasty-plugin-sdk`, `tasty-plugin-sdk-wasm`: 플러그인 공통 라이브러리, 매니페스트, 통신 형식, SDK, WASM 실험이다. 플러그인 시스템을 지원하지 않으므로 앱 기능 목록에 해당하지 않는다.

### 3.4 원격에 기능이 없을 때의 시각적 피드백 (전제 5)

전제는 "시각적 피드백만 보여 준다"이다. 아래는 그런 피드백이 필요한 경우의 후보다. 어떤 형태(배너, 빈 화면 안내, 비활성 표시 등)로 보여 줄지는 정하지 않았다.

| 경우 | 예 |
|---|---|
| 원격에 `git`이 없다 | Git 정보 화면에서 "원격에 git이 없음"을 보여 준다 |
| 대상 폴더가 git 저장소가 아니다 | Git 정보를 비활성으로 보여 준다 |
| SFTP 서브시스템이 꺼져 있다 | Explorer를 열 수 없다는 표시 |
| 원격 Tasty가 없거나 실행 중이 아니다 | 원격 Tasty 관련 화면(4.3에서 넣기로 할 때)을 비활성으로 보여 준다 |
| 원격 Tasty 버전이 맞지 않거나 필요한 플러그인이 꺼져 있다 | 해당 기능 화면에 이유를 표시 |
| 권한이 없다 | 읽을 수 없는 파일·폴더 표시 |

## 4. 열린 선택지

지침이 "아직 정하지 않았다"고 한 범위다. 각 항목은 선택지와 장단점만 적는다.

### 4.1 앱의 1차 사용 장면

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 원격 파일 열람 위주 (Explorer + 뷰어 + Git 정보) | 전제 3, 4와 바로 맞는다. 범위가 가장 작다 | 데스크톱 Tasty와의 연결점이 약하다 |
| B. 원격 Tasty 동반 앱 (원격 Tasty의 워크스페이스·에이전트 상태를 보고 다룬다) | Tasty 사용자에게 고유한 가치가 있다 | 원격 Tasty와의 통신 범위(4.3)를 먼저 정해야 한다 |
| C. 독립 SSH 터미널 + 파일 | 원격 Tasty 없이도 쓸 수 있다 | 기존 모바일 SSH 앱과 겹친다. 터미널 구현 비용이 크다 |
| D. A에서 시작해 B나 C로 넓힌다 | 단계적으로 진행할 수 있다 | 처음 구조를 넓힐 수 있게 잡아야 한다 |

### 4.2 터미널(셸) 기능

| 선택지 | 장점 | 단점 |
|---|---|---|
| 넣지 않는다 | 범위가 작다. 모바일 키보드 문제를 피한다 | 원격에서 명령을 직접 실행할 수 없다 |
| 원격 명령 한 번 실행 후 결과만 본다 | 구현이 작다. Git 정보와 같은 실행 경로를 쓴다 | 대화형 프로그램은 쓸 수 없다 |
| 대화형 SSH 터미널을 넣는다 | 원격 작업을 모두 할 수 있다 | 터미널 에뮬레이션, 입력, 렌더링 비용이 크다(5절 터미널 크레이트 참고) |
| 원격 Tasty 서피스의 화면을 보거나 입력을 보낸다 | Tasty의 기존 서피스를 이어서 쓸 수 있다 | 원격 Tasty와의 관계(4.3)에 묶인다 |

### 4.3 원격 Tasty와의 관계

제약: 본체에 전용 채널을 추가하지 않는다(전제 4).

| 선택지 | 장점 | 단점 |
|---|---|---|
| 연동하지 않는다 | 원격 Tasty가 없어도 같은 기능을 쓴다 | Tasty 앱으로서의 차별점이 적다 |
| 본체에 이미 있는 원격 조회(워크스페이스 목록·생성)를 SSH 위에서 쓴다 | 본체를 바꾸지 않는다 | 본체의 원격 기능이 시스템 ssh와 포트 터널을 쓰므로 Android에서 같은 방식을 다시 구현해야 한다 |
| 원격에서 `tasty` CLI를 SSH 명령으로 실행해 결과를 읽는다 | Git 정보와 같은 방식이다. 본체를 바꾸지 않는다 | 원격 `tasty`가 PATH에 없을 때의 처리가 필요하다. CLI 출력 형식이 계약이 된다 |
| attach(서피스 복제 화면)까지 한다 | 데스크톱과 가장 가깝다 | 범위가 가장 크다. 모바일은 다른 형태로 만든다는 전제 1과 충돌할 수 있다 |

### 4.4 파일 편집

| 선택지 | 장점 | 단점 |
|---|---|---|
| 읽기 전용 | 데이터 손상 위험이 없다. 범위가 작다 | 간단한 수정도 할 수 없다 |
| 텍스트 파일만 편집 | 자주 쓰는 수정을 할 수 있다 | 충돌(다른 곳에서 동시에 바뀐 파일) 처리가 필요하다 |
| 파일 관리(이름 바꾸기·삭제·업로드)까지 | 파일 관리자로 쓸 수 있다 | 실수로 지우는 위험, 확인 UI가 필요하다 |

### 4.5 SSH 인증과 키 보관, 접속 프로필 형식

인증 방식:

| 선택지 | 장점 | 단점 |
|---|---|---|
| 비밀번호만 | 구현이 쉽다 | 보안이 약하다. 많은 서버가 막아 둔다 |
| 공개키(앱에서 생성, Android Keystore로 보호) | 키가 기기 밖으로 나가지 않는다 | Keystore가 지원하는 키 종류(예: Ed25519 지원 여부)를 기기별로 확인해야 한다 |
| 공개키(가져오기) | 기존 키를 그대로 쓴다 | 개인 키 파일을 기기로 옮기는 위험이 있다 |
| 하드웨어 키·에이전트 연동 | 보안이 가장 좋다 | 구현과 지원 기기 범위가 어렵다 |

접속 프로필 형식:

| 선택지 | 장점 | 단점 |
|---|---|---|
| 본체의 `remote-profiles.toml` 형식과 맞춘다 | 데스크톱 설정을 옮길 수 있다 | 본체 형식이 바뀌면 따라가야 한다. 비밀(passkey) 보관 방식은 모바일에서 다르게 해야 한다 |
| 앱 고유 형식 | 모바일에 맞게 단순하게 만든다 | 데스크톱과 설정을 공유할 수 없다 |
| 앱 고유 형식 + 가져오기 기능 | 둘의 장점을 함께 얻는다 | 변환 코드를 유지해야 한다 |

### 4.6 SSH/SFTP 구현 방식

| 선택지 | 장점 | 단점 |
|---|---|---|
| JVM/Kotlin 라이브러리 | Android에서 바로 쓴다. 빌드가 단순하다 | 라이브러리마다 지원 알고리즘과 유지 상태가 다르다. 본체와 로직을 공유하지 않는다 |
| Rust SSH 라이브러리를 UniFFI로 감싼다 | 프로필·오류 처리 등을 Rust 쪽에서 본체와 맞출 여지가 있다 | 본체의 `tasty-ssh`는 시스템 ssh 프로세스를 쓰므로 그대로 공유할 수 없다. NDK 빌드가 생긴다 |
| 기기의 외부 SSH 앱이나 시스템에 맡긴다 | 구현이 작다 | Android에는 기본 ssh가 없다. 사용자 설치에 기댄다 |

### 4.7 지원 기기·폼팩터와 minSdk

| 선택지 | 장점 | 단점 |
|---|---|---|
| 폰만 | 화면 설계가 하나다 | 태블릿에서 파일·코드를 보기에는 좁은 화면을 늘려 쓰게 된다 |
| 폰 + 태블릿(적응형 레이아웃) | 큰 화면에서 Explorer와 뷰어를 나란히 볼 수 있다 | 레이아웃과 시험이 늘어난다 |
| 태블릿·폴더블 우선 | 코드 열람에 맞는 화면이다 | 사용자 수가 적다 |

minSdk:

- 골격 기본값: 29 (Android 10). 골격 작업이 고른 기본값이며 제품 결정이 아니다. 골격 쪽 이유는 사용 중인 기기 대부분을 덮고, scoped storage와 TLS 1.3 기본값을 전제할 수 있으며, 오래된 API 분기를 줄인다는 것이다. 같은 골격의 compileSdk·targetSdk는 37이다.
- 선택지: 골격 기본값을 유지한다 / 낮춰 오래된 기기를 지원한다 / 높여 최신 API(예: Keystore 기능)를 쓴다. 높일수록 지원 기기가 줄고, 낮출수록 대체 구현이 늘어난다.

### 4.8 오프라인·캐시 범위

| 선택지 | 장점 | 단점 |
|---|---|---|
| 캐시하지 않는다(항상 원격에서 읽는다) | 항상 최신이다. 기기에 데이터가 남지 않는다 | 연결이 끊기면 아무것도 볼 수 없다. 데이터 사용량이 늘어난다 |
| 최근 연 파일·목록만 캐시 | 다시 열 때 빠르다 | 오래된 내용을 보여 줄 수 있어 표시가 필요하다 |
| 사용자가 고른 폴더를 오프라인으로 보관 | 연결 없이 볼 수 있다 | 동기화와 저장 공간 관리가 필요하다 |

### 4.9 배포 경로

| 선택지 | 장점 | 단점 |
|---|---|---|
| Google Play | 설치와 업데이트가 쉽다 | 심사, 개발자 계정, 정책(권한·데이터 안전 표시)을 맞춰야 한다 |
| GitHub 릴리스(APK) | 빠르게 배포한다. 공개 레포와 맞는다 | 사용자가 직접 설치하고 업데이트해야 한다 |
| F-Droid | 오픈소스 사용자에게 맞는다 | 재현 가능한 빌드 등 요구 조건이 있다 |
| 여러 경로를 함께 | 사용자층이 넓어진다 | 서명과 릴리스 관리가 늘어난다 |

applicationId·namespace: 골격은 임시 값 `dev.tasty.android`를 쓴다. 기존 Tasty 패키지 관례를 찾지 못해 고른 값이며, 정해야 할 항목이다(배포 뒤에는 바꾸기 어렵다).

## 5. 공유 Rust 크레이트 후보

- **이번 골격에는 UniFFI와 Rust 크레이트를 넣지 않았다.** 아래는 후보일 뿐이며 어느 것을 공유할지 정하지 않았다.
- 기준: 공개 레포 github.com/zilhak/tasty `89efb5602`의 `crates/*/Cargo.toml`.

| 크레이트 | 하는 일 (description 요약) | 공유하는 이유 | 걸림돌 |
|---|---|---|---|
| `tasty-git-core` | git2 기반 읽기 전용 래퍼(저장소 찾기, status/log/diff/worktree) | 본체와 같은 Git 정보 모델을 쓸 수 있다 | 전제 4는 원격 `git` 명령으로 읽는다고 정했다. git2(libgit2)는 로컬 저장소를 읽으므로 그대로는 맞지 않는다. 결과 타입만 공유하거나, `git` 명령 출력 파싱을 새로 나눠 공유하는 선택지가 있다 |
| `tasty-remote-profiles` | 원격 접속 프로필과 passkey(`~/.tasty/remote-profiles.toml`, `passkeys.toml`) | 프로필 형식을 본체와 맞출 때(4.5) 같은 파서를 쓴다 | 파일 경로가 데스크톱 홈 폴더 기준이다. 비밀 보관은 Android Keystore 쪽으로 바꿔야 한다 |
| `tasty-ssh` | 시스템 ssh 프로세스 실행, 터널, 원격 포트 찾기 | 본체의 원격 연결 동작과 같은 순서를 쓸 수 있다 | Android에는 시스템 ssh가 없다. 프로세스 실행에 기대므로 **그대로는 후보가 되기 어렵다**. 재시도·취소 정책만 떼어 낼 수 있는지가 쟁점이다 |
| `tasty-remote` | 원격 tasty의 워크스페이스 조회·생성 클라이언트 | 원격 Tasty 연동(4.3)을 할 때 같은 요청 형식을 쓴다 | `tasty-ssh`, `tasty-ipc`, `tasty-model`, `tokio`에 의존한다. SSH 전송 부분을 갈아 끼울 수 있어야 한다 |
| `tasty-file-format`, `tasty-file-handler` | 파일 형식 판별, 형식별 핸들러 정책(Domain-only) | Explorer에서 파일을 어떤 뷰어로 열지 본체와 맞춘다 | `mlua`(Lua 엔진 내장)와 `tasty-plugin-protocol`에 의존한다. 플러그인 기여(contribution) 개념은 모바일에 해당하지 않는다. 판별 결과가 본체와 같아야 하는지부터 정해야 한다 |
| `tasty-terminal`, `tasty-ansi`, `tasty-cell-width`, `tasty-selection`, `tasty-terminal-link` | 터미널 에뮬레이션, ANSI 제거, 셀 폭, 선택, 링크 찾기 | 터미널 기능(4.2)을 넣을 때 본체와 같은 동작을 얻는다 | `tasty-terminal`은 PTY(`portable-pty`)를 포함한다. 원격 셸에는 로컬 PTY가 필요 없으므로 VTE 부분만 쓸 수 있는지 확인해야 한다. `tasty-ansi`·`tasty-cell-width`는 작아서 터미널 없이도 출력 정리에 쓸 수 있다 |
| `tasty-design-tokens`, `tasty-themes` | 디자인 토큰(DTCG), 테마 파일 | 색·크기를 본체와 맞춘다 | 모바일은 다른 형태로 만든다(전제 1). 토큰 JSON만 Compose 테마로 변환해 쓰면 Rust 공유 없이 해결될 수 있다 |
| `tasty-i18n` | 번역 테이블 불러오기와 조회 | 번역 문자열을 본체와 공유한다 | Android는 문자열 리소스 체계가 따로 있다. `ab_glyph`(글꼴) 의존이 있다. 번역 파일만 변환해 쓰는 선택지가 있다 |
| `tasty-model` | 워크스페이스/페인/탭/서피스 도메인 모델 | 원격 Tasty 연동(4.3)에서 같은 모델을 쓴다 | 연동하지 않으면 필요 없다 |
| `tasty-ipc` | IPC 프레이밍, 세션, 메서드 목록 | 원격 Tasty와 직접 통신할 때 필요하다 | 전제 4(본체에 전용 채널 없음) 안에서 쓸 방법이 있는지 확인해야 한다 |
| `tasty-key-match` | 단축키 문자열과 키 이벤트 맞추기 | 하드웨어 키보드 단축키를 본체와 맞출 때 | 터치 중심 앱에서는 쓸모가 작다 |
| `tasty-output` | 출력 의미 분석(경로, URL, 프롬프트, 종료 코드) | 원격 명령 결과에서 경로·URL을 찾을 때 | 터미널이나 명령 실행 기능이 있어야 쓸모가 있다 |

공통 걸림돌:

- UniFFI를 쓰면 NDK 빌드(Android ABI별 Rust 빌드)와 CI 구성이 추가된다.
- 공유 크레이트가 본체 레포에 있으므로 버전 고정 방식(git 의존 + sha 고정, 별도 배포 등)을 정해야 한다. 이 결정에 따라 본체 레포 변경이 필요해질 수 있다.

## 6. 모바일 원칙 (정해야 할 항목)

전제 1에 따라 데스크톱 원칙을 그대로 쓰지 않는다. 아래는 정해야 할 질문만 적고 답은 적지 않는다.

1. 한 화면에 몇 가지를 동시에 보여 주는가? (데스크톱의 분할·탭 구조를 어느 정도 가져오는가)
2. 기본 입력은 터치인가, 하드웨어 키보드도 1급으로 지원하는가?
3. 연결이 끊기거나 느릴 때 앱은 어떻게 동작해야 하는가?
4. 원격 데이터를 바꾸는 동작(편집, 삭제, 명령 실행)에 어떤 확인 단계를 두는가?
5. 비밀(키, 비밀번호)은 어디에 어떻게 보관하고, 기기를 잃어버렸을 때 무엇을 기대하는가?
6. 백그라운드에서 연결을 유지하거나 알림을 받는가? (배터리와 Android 백그라운드 제한)
7. 본체와 맞춰야 하는 것(형식, 동작)과 모바일이 따로 가도 되는 것의 경계는 어디인가?
8. 기능이 없을 때의 시각적 피드백(전제 5)은 어떤 일관된 모양을 가지는가?
